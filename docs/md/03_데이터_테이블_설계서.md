# 여행말 데이터 테이블 설계서

| 항목 | 내용 |
| --- | --- |
| 문서명 | 데이터 테이블 설계서 (통합본) |
| 버전 | v0.5 — 팀 설계서 v0.4 + ERD + 프론트·API 명세와 정합 |
| DBMS | MySQL 8.0 (Cloud DB for MySQL) |
| 문자셋 / 콜레이션 | utf8mb4 / utf8mb4_general_ci |
| 개발 마감 | 2026-10-16 |
| 함께 보는 문서 | 01 아키텍처 구상도 · 02 ERD · 04 API 기능명세서 · 05 프론트엔드 기능명세서 |

> 이 문서가 **데이터 구조의 유일한 기준**이다. 02 ERD는 이 문서의 그림 버전이고, 04 API 명세 7장은 응답 항목이 어느 컬럼에서 나오는지 연결한다. 팀 설계서 v0.4와 ERD(10개 테이블) 사이의 충돌은 1.3장의 공통 결정(C-xx)으로 정리했다.

## 1. 문서 정보

### 1.1 서비스 요약

- 가입·로그인 없이 닉네임만으로 시작한다. 서버가 발급한 쿠키로 같은 브라우저를 알아본다(6장).
- 책 1권 = 여행 1건, 여행 N일 = 챕터 N개(하루 1챕터). 문체를 바꾸면 챕터에 새 버전이 생긴다.
- 모든 문장은 사진 또는 사용자 발화에서만 만들고, **문장마다** 근거(사진·발화)를 저장한다.
- 사진 없는 시간 공백(14:00~16:50)을 질문 후보로 쓴다(장면의 GAP 유형).
- 사진 분석, 챕터 작성, 책 엮기, 문체 변경은 비동기 작업(진행·실패·재시도)이며 tb_job으로 관리한다. 질문 생성과 답변 전사는 화면이 기다리므로 동기로 처리한다.
- 사진·음원 파일은 DB에 넣지 않고 Object Storage 객체 키(`*_key`)만 저장한다.

### 1.2 이번 통합에서 바뀐 것 (v0.4 → v0.5)

| # | 변경 | 이유 |
| --- | --- | --- |
| 1 | `tb_chapter_paragraph`, `tb_paragraph_evidence` → `tb_chapter_sentence`, `tb_sentence_evidence` | 리더가 "문장"을 눌러 근거를 보여 주므로 근거는 문장 단위여야 한다(ERD의 STORY_SENTENCE 방식). 테이블 수는 14개 그대로 |
| 2 | `tb_photo.place_source` VARCHAR(10) → 20 | 값 `AI_ESTIMATE`가 11자라 저장되지 않음 |
| 3 | `tb_chapter`에 `subtitle`, `moments`, `photo_id`, `highlight_voice_segment_id`, `highlight_text` 추가 | 챕터 부제·포착 순간 칩·본문 사진·대표 인용(그때 내 목소리)을 저장할 곳이 없었음 |
| 4 | `tb_trip.cover_photo_id` 추가, `cover_color_set`을 책등 색으로 정의, `day_count` 삭제 | 표지는 사진 배경 + 제목으로 고정. 일수는 날짜로 계산 |
| 5 | `time_source`에서 FILE 삭제 | 서버는 업로드 파일의 시각을 알 수 없음. 시각이 없으면 NULL |
| 6 | `tb_job.active_key` 추가, `JOB_TYPE` 정리(RESTYLE 추가, QUESTION_GEN·GAP_DETECT·MEMORY_EXTRACT·PDF_EXPORT 삭제) | 같은 대상의 중복 작업 방지(MySQL은 부분 유니크 인덱스가 없음), 문체 변경 작업 유형 누락, 동기 처리하는 작업은 작업 테이블에서 제외 |
| 7 | 공통 코드 그룹 보강, COVER_TYPE 삭제 | 상태값이 문서마다 달랐음 |
| 8 | `tb_user`에서 `notify_time`, `deleted_at` 삭제 | 화면·API에 없음. 삭제는 물리 삭제(11장) |
| 9 | 삭제 절차(ERD 7장)를 채택, `DELETE_PENDING`·`DELETING` 상태 추가 | CASCADE만 쓰면 Object Storage 파일이 남음 |
| 10 | 유일 현재 버전 / 활성 작업을 생성 컬럼 + 유니크 키로 보장 | `current_yn`·활성 작업 중복을 DB가 막지 못했음 |

### 1.3 공통 결정 (C-xx) — 5개 문서가 같은 값을 쓴다

| ID | 결정 | 비고 |
| --- | --- | --- |
| C-01 | 스키마 기준 = 이 문서(tb_* 14개) + 문장 단위 근거 + ERD의 삭제 절차 | |
| C-02 | 사용자 식별 = 쿠키 `yeohaengmal_token`(HttpOnly, Secure, SameSite=Lax, Path=/), 유효 180일(접속 때마다 연장), DB에는 SHA-256 해시(CHAR 64) | ▲ 이름·기간 팀 확인 |
| C-03 | 쿠키를 잃으면(삭제·다른 브라우저·시크릿 창) 기존 책장은 복구할 수 없다 = 의도된 정책 | ▲ 팀 확인 |
| C-04 | 모든 API는 `/api` 접두. 프론트·API는 같은 출처 | 01 참조 |
| C-05 | 문체 코드 = ESSAY / EMOTIONAL / FAIRYTALE. **NOVEL 제외**(화면 없음). 문체 변경은 포함(챕터 버전) | ▲ 소설이 필요하면 화면과 함께 추가 |
| C-06 | PDF 내보내기 = MVP 제외(프론트는 시연용 안내만). 서버 API·작업 없음 | |
| C-07 | 촬영 시각 = EXIF만(`EXIF`/`NONE`). 시각 없는 사진은 NULL로 저장하고 직전 장면에 편입, 직전 장면이 없으면 "시간 미상" 장면을 만든다 | |
| C-08 | 질문 = 동적 생성, 5개 고정. 순서 GAP(가장 긴 공백) → PLACE × 3 → CLOSING | 순서·개수는 시연 데이터로 조정 |
| C-09 | 건너뜀·빈 전사는 `SKIPPED`, "답한 질문 수"에 세지 않는다 | |
| C-10 | 인터뷰 종료 = DONE(5개 완료) / SAVE_EXIT(저장하고 마침) / DISCARD(저장 안 함). 이어 하기는 첫 `ASKED` 질문부터 | |
| C-11 | 음성은 발화 단위(tb_voice_segment). `keep_audio_yn=N`이면 `audio_key`는 NULL(전사 후 파일 삭제) | |
| C-12 | 비동기 작업 = PHOTO_ANALYZE / CHAPTER_WRITE / BOOK_BIND / RESTYLE. 질문 생성·전사·질문 음성 합성은 동기. 장면별 재료 정리(tb_scene_memory)는 챕터 작성 1단계에서 한다 | |
| C-13 | 수치 기본값: 장면 분할 40분·300m, 공백(GAP) 90분 이상, 여행 최대 30일, 사진 1회 1~200장, 답변 55초(서버 60초 초과는 거부), 업로드 URL 15분, 열람 URL 1시간 | 시연 데이터로 조정 |
| C-14 | 재시도 한도 = MVP에서는 제한 없음(▲ 제안: 3회), 챕터 작성 제한 시간 180초(▲ 제안) | |
| C-15 | 촬영 날짜가 일차 날짜와 달라도 올린 일차에 저장한다 | |
| C-16 | 책 엮기 = 완료(DONE)된 챕터만 포함, 0개면 400, 작성 중(WRITING)이 있으면 409 | |
| C-17 | 진행 중 여행은 1개. WRITING / BINDING / FAILED 여행이 있으면 새 여행은 409 | DB는 막지 못하므로 사용자 행을 잠근 트랜잭션에서 검사 |
| C-18 | 표지 = 사진 배경 + 제목 고정. 표지 사진 = 사진 수가 가장 많은 장면의 대표 사진. `cover_color_set` 1~4 = 책등 색(1 red, 2 teal, 3 navy, 4 slate) | |
| C-19 | API의 ID는 문자열(DB BIGINT를 그대로 문자열로 직렬화) | |
| C-20 | 음성 인식 = CLOVA Speech Recognition(1회 60초), 음성 합성 = CLOVA Voice TTS Premium | |

▲ = 팀이 최종 확인해야 하는 값.

## 3. 테이블 상세 정의

공통 컬럼 `id`(BIGINT UNSIGNED, PK, AUTO_INCREMENT), `created_at`(DATETIME NOT NULL, 기본 CURRENT_TIMESTAMP), `updated_at`(DATETIME NULL, ON UPDATE CURRENT_TIMESTAMP)은 공통 코드를 뺀 모든 테이블에 있으며 아래 표에서는 생략한다(tb_sentence_evidence는 `updated_at` 없음). 서버 처리 시각은 UTC, 사진 촬영 시각·여행 날짜는 현지(한국) 시각·날짜로 저장한다.

### 3-1. tb_user (사용자)

- 로그인 없이 닉네임을 만들어 시작하는 사용자. 쿠키로 같은 사용자를 알아본다. 설정 화면 값 포함.
- 삭제: 설정 > "내 데이터 삭제"(11장).

| 컬럼명 | 한글명 | 타입 | NULL | 기본값 | 설명 |
| --- | --- | --- | --- | --- | --- |
| browser_token_hash | 브라우저 식별 토큰(해시) | CHAR(64) | N | | 쿠키 토큰의 SHA-256 hex. UNIQUE. 원본은 저장하지 않음 |
| last_access_at | 마지막 접속일시 | DATETIME | Y | | 쿠키로 접속할 때마다 갱신 |
| nickname | 닉네임 | VARCHAR(20) | N | | 앞뒤 공백 제거 후 1~20자. "OO님의 책장"에 표시. 중복 허용 |
| interviewer_voice | 인터뷰어 목소리 | VARCHAR(20) | N | CALM | 코드 VOICE_TYPE (CALM / BRIGHT / PLAIN) |
| keep_audio_yn | 원본 음성 보관 | CHAR(1) | N | Y | N이면 답변 음성은 전사 후 삭제하고 `audio_key`를 저장하지 않음 |

- 인덱스: UNIQUE `uk_user_token(browser_token_hash)`
- 제약: `ck_user_nickname` CHECK (CHAR_LENGTH(TRIM(nickname)) BETWEEN 1 AND 20)

### 3-3. tb_trip_day (여행 일차)

| trip_id | 여행 | BIGINT UNSIGNED | N | | FK tb_trip |

### 3-8. tb_voice_segment (음성 발화)

| 컬럼명 | 한글명 | 타입 | NULL | 기본값 | 설명 |

| interview_id | 인터뷰 | BIGINT UNSIGNED | N | | FK tb_interview |

| --- | --- | --- | --- | --- | --- |

| trip_day_id | 일차 | BIGINT UNSIGNED | N | | FK tb_trip_day |
| chapter_no | 챕터 번호 | SMALLINT | N | | 목차 01, 02… (책 엮기 때 일차순으로 확정) |
| title | 챕터 제목 | VARCHAR(100) | Y | | "비 오는 날의 손님" |
| subtitle | 부제 | VARCHAR(100) | Y | | "비 오는 전주" → 화면 "2일차 · 비 오는 전주" |
| moments | 포착 순간 | JSON | Y | | 문자열 배열(예: ["대나무 숲 소리", …]) |

| version | 버전 | SMALLINT | N | 1 | 같은 일차·문체 안의 버전(새로 쓸 때 최대값 + 1) |
| current_yn | 현재 버전 | CHAR(1) | N | Y | 일차당 Y는 1개 |
| current_key | (생성 컬럼, VIRTUAL) | BIGINT UNSIGNED | | | `IF(current_yn='Y', trip_day_id, NULL)` — UNIQUE로 현재 버전 1개 보장. MySQL은 STORED 생성 컬럼의 기반 컬럼(trip_day_id)에 CASCADE FK를 걸 수 없으므로 VIRTUAL로 둔다 |

| retry_cnt | 재시도 횟수 | TINYINT | N | 0 | "다시 쓰기"마다 +1 |

### 3-11. tb_sentence_evidence (문장 근거)

| 컬럼명 | 한글명 | 타입 | NULL | 기본값 | 설명 |
| --- | --- | --- | --- | --- | --- |

| UPLOAD_STATUS | UPLOADING / READY / FAILED / DELETE_PENDING | 올리는 중 / 완료 / 실패 / 삭제 대기 |
| PROCESS_STATUS | PENDING / DONE / FAILED | 대기 / 완료 / 실패(사진 분석·장면 기억 추출) |
| TIME_SOURCE | EXIF / NONE | 촬영 시각 / 없음 |
| PLACE_SOURCE | EXIF_GPS / OCR / AI_ESTIMATE / NONE | GPS 좌표 / 사진 속 텍스트 / AI 추정 / 없음 |
| JOB_TYPE | PHOTO_ANALYZE / CHAPTER_WRITE / BOOK_BIND / RESTYLE | 사진 분석 / 챕터 작성 / 책 엮기 / 문체 변경 |
| JOB_STATUS | QUEUED / RUNNING / DONE / FAILED | 대기 / 진행 / 완료 / 실패 |
| FAIL_CODE | ANALYZE_ERROR / WRITE_ERROR / WRITE_TIMEOUT / EMPTY_AFTER_FILTER / BIND_ERROR / RESTYLE_ERROR / UPSTREAM_ERROR / SERVER_RESTART | 사진 분석 오류 / 작성 오류 / 작성 시간 초과 / 근거 검증 후 남은 문장 없음 / 책 엮기 오류 / 문체 변경 오류 / 외부 서비스 오류 / 서버 재시작으로 중단 |
| VALIDATION_ERR | NICKNAME_EMPTY / NICKNAME_TOO_LONG | 닉네임 미입력 / 닉네임 길이 초과 |

## 6. 사용자 식별 (브라우저 쿠키)

### 6-1. 방식

- 로그인 없이 쿠키로 사용자를 구별한다. 닉네임 생성에 성공하면 서버가 무작위 토큰을 만들어 쿠키로 내려주고, 다음 접속 때 같은 쿠키가 있으면 기존 사용자로 들어간다.
- 쿠키에는 서버가 발급한 무작위 토큰만 넣는다(닉네임·사용자 번호 같은 추측 가능한 값은 넣지 않는다). 서버에는 해시만 저장한다.
- 닉네임은 사용자를 구별하는 값이 아니다. 같은 닉네임이 있어도 되며 구별은 쿠키로만 한다.

| 항목 | 내용 |
| --- | --- |
| 쿠키 이름 | `yeohaengmal_token` (▲ 팀 확인) |
| 쿠키 값 | 서버가 발급한 무작위 토큰(32바이트 이상) |
| 발급 시점 | 닉네임 검증 통과 + tb_user 저장 성공 시에만 |
| 보안 속성 | HttpOnly, Secure, SameSite=Lax, Path=/ |
| 유효 기간 | 180일, 접속(GET /users/me 포함)할 때마다 연장 (▲ 팀 확인) |
| 닉네임 변경 | 쿠키·토큰은 그대로 |
| 화면의 로그인 확인 | HttpOnly라 화면이 쿠키를 읽을 수 없으므로 `GET /users/me`(401이면 /start)로 확인 |

### 6-2. 접속 상황별 처리

| No | 상황 | 조건 | 처리 | 화면 |
| --- | --- | --- | --- | --- |
| 1 | 첫 방문 | 쿠키 없음 | 새 사용자로 보고 닉네임 입력으로 안내 | 온보딩 |
| 2 | 닉네임 생성 성공 | 검증 통과, 저장 성공 | 토큰 생성 → 해시 저장 → 쿠키 발급 | "OO님의 책장" |
| 3 | 닉네임 생성 실패 | 검증·저장 실패 | 쿠키도 사용자도 만들지 않음 | 오류 안내, 입력 화면 유지 |
| 4 | 재방문, 쿠키 일치 | 해시가 tb_user와 일치 | 기존 사용자, `last_access_at` 갱신 | 바로 책장 |
| 5 | 재방문, 일치하는 사용자 없음 | 쿠키는 있으나 tb_user에 없음 | 쿠키 만료(Set-Cookie)와 함께 401 | 온보딩 |
| 6 | 쿠키 없는 환경 | 쿠키 삭제, 다른 브라우저, 시크릿 창 | 새 사용자로 처리. 기존 책장 복구 불가(C-03) | 온보딩 |
| 7 | 쿠키 차단 브라우저 | 쿠키 저장 불가 | 계정이 유지되지 않음(안내 문구 미정) | 곧 /start로 돌아옴 |
| 8 | 내 데이터 삭제 | 설정 > 내 데이터 삭제 | 11장 절차 후 쿠키 만료 | 온보딩 |

## 7. AI 질문·스토리 생성 흐름

### 7-1. 전체 처리 흐름

| No | 단계 | 처리 | 방식 | 저장 위치 |
| --- | --- | --- | --- | --- |
| 1 | 사진 업로드 | 하루 단위로 한 번에 올림(브라우저 → Object Storage 직접) | 동기 | tb_photo(UPLOADING → READY) |
| 2 | 시간 추출 | EXIF 촬영 시각. 없으면 NULL (C-07) | 작업(PHOTO_ANALYZE) | tb_photo.taken_at, time_source |
| 3 | 장소·위치 추출 | GPS → 장소명(Reverse Geocoding), 간판·메뉴 글자(OCR, 선택) | 작업 | tb_photo.latitude, longitude, place_name, place_source, ocr_text, caption |
| 4 | 장면 묶기·빈 시간 | 시간·거리 가까운 사진을 장면으로 묶고, 사이의 공백이 길면 GAP 장면 생성 | 작업 | tb_scene (PHOTO, GAP), gap_min |
| 5 | 질문 생성 | 답변이 확정될 때마다 이전 대화·장면을 반영해 다음 질문 1개를 만든다 | **동기**(API 안) | tb_interview_question |
| 6 | 음성 인터뷰 | 질문 TTS 재생 → 사용자 답변 녹음 → 전사 | **동기** | tb_voice_segment |
| 7 | 장면 재료 정리 | 전사·사진 정보에서 행동·느낌·장소·사진 속 텍스트 추출 | 작업(CHAPTER_WRITE 1단계) | tb_scene_memory |
| 8 | 스토리 작성 | 장면 재료를 시간순으로 엮어 선택한 문체로 쓰고 근거 없는 문장은 거름 | 작업(CHAPTER_WRITE 2~5단계) | tb_chapter, tb_chapter_sentence, tb_sentence_evidence |
| 9 | 책 엮기 | 일차별 챕터를 모아 제목·표지·근거 재확인 | 작업(BOOK_BIND) | tb_trip(status, title, cover_photo_id, cover_color_set), tb_chapter(chapter_no) |
| 10 | 문체 변경 | 같은 재료로 새 버전 챕터를 만들고 한 번에 교체 | 작업(RESTYLE) | tb_chapter(version + 1), tb_trip.writing_style |

### 7-2. 질문 생성 기준

- 질문은 사진의 시간·장소·텍스트에서 근거를 찾을 수 있는 것만 만들고, 근거 장면·사진·설명을 함께 저장한다(`scene_id`, `photo_id`, `basis_text`).
- 질문 5개 고정(C-08). 순서: ① 가장 긴 GAP 장면 1개 → ② 사진이 많거나 간판·메뉴가 읽힌 장면(PLACE) 3개 → ③ 마지막 고정 질문 "오늘 하루를 한 단어로 하면요?"(CLOSING). GAP이 없으면 PLACE 질문이 앞선다.
- 건너뛴 질문(SKIPPED)의 장면은 답변 없이 사진 정보만으로 쓴다. 이후 질문은 아직 묻지 않은 장면을 우선한다.

| 질문 유형 | 생성 조건 | 예시 | 근거 저장 |
| --- | --- | --- | --- |
| GAP | 사진 없는 구간이 있을 때 | "3시부터 5시까지는 사진이 한 장도 없네요. 그때 뭐 하셨어요?" | scene_id, basis_text |
| PLACE | 장소가 추출된 장면 | "경기전에서는 무엇을 하셨어요? 그때 어떤 느낌이었어요?" | scene_id, photo_id, basis_text |
| CLOSING | 마지막 질문 | "오늘 하루를 한 단어로 하면요?" | 없음 |

## 9. 입력 검증·실패 처리

### 9-1. 닉네임 입력 검증

- 대상: 온보딩 "뭐라고 불러 드릴까요?"
- 규칙: 앞뒤 공백 제거 후 1~20자. 화면(입력 제한 20자 + 빈 값 검사) → API(400) → DB(CHECK) 순으로 세 번 검증.
- 오류 문구는 화면에서만 쓰고 DB에는 저장하지 않는다. tb_user는 검증 통과 후에만 생성한다.

| 상황 | 입력값 | 화면 동작 | 데이터 처리 |
| --- | --- | --- | --- |
| 기본 | 미입력 | 안내 문구, 버튼 비활성 | 저장 없음 |
| 길이 부족 | 빈 값 / 공백만 | "닉네임을 한 글자 이상 입력해 주세요" | tb_user 미생성 (NICKNAME_EMPTY) |
| 정상 | 1~20자 | "OO님의 책장" 미리보기 후 책장으로 이동 | tb_user 생성, 쿠키 발급 |
| 길이 초과 | 21자 이상 | 입력창이 받지 않음 | API가 400 (NICKNAME_TOO_LONG) |

### 9-2. 작성·처리 실패

- 실패해도 사진·음성·전사는 보존한다("대화는 저장돼 있어요").
- 실패 단위는 일차(챕터)다. 한 일차의 실패가 다른 일차에 영향을 주지 않는다.
- "다시 쓰기"는 같은 일차에 새 작업과 새 챕터 행(version + 1)을 만들고 `retry_cnt`를 올린다. 이전 실패는 tb_job에 이력으로 남는다.
- 화면을 닫아도 서버는 계속 처리한다. 서버가 재시작되면 RUNNING 작업은 FAILED(`SERVER_RESTART`)로 바꾼다.

| No | 상황 | 화면 안내 | 데이터 처리 | 상태·코드 |
| --- | --- | --- | --- | --- |
| 1 | 챕터 작성 실패 | "이야기를 다 쓰지 못했어요 / 대화는 저장돼 있어요" | tb_chapter.status=FAILED, tb_trip_day.status=FAILED, tb_job FAILED | WRITE_ERROR |
| 2 | 근거 검증 후 남은 문장 없음 | 1번과 같음 | 근거 없는 문장은 저장하지 않고 남은 문장이 0개면 실패 | EMPTY_AFTER_FILTER |
| 3 | 작성 시간 초과 | 1번과 같음 | tb_job FAILED, 챕터 FAILED | WRITE_TIMEOUT |
| 4 | 책 엮기 실패 | "책을 엮지 못했어요 / 기록한 이야기는 모두 저장돼 있어요" | 챕터 전부 보존, tb_trip.status=FAILED, tb_job FAILED | BIND_ERROR |
| 5 | 사진 분석 실패 | "사진은 모두 저장됐어요. 장면을 묶지 못했어요." | 원본 사진 보존. 일부 실패한 사진은 analysis_status=FAILED로 두고 나머지로 장면 구성, 전부 실패면 tb_trip_day.status=FAILED | ANALYZE_ERROR |
| 6 | 문체 변경 실패 | "다시 쓰지 못했어요. 지금 책은 그대로 있어요." | 새 버전은 버리고 기존 current 유지 | RESTYLE_ERROR |
| 7 | 인터뷰를 중간에 마침 | "지금까지 답한 질문 n개는 저장돼요. 남은 질문 m개는 건너뛰어요." | SAVE_EXIT: ASKED 질문을 SKIPPED, end_type=SAVE_EXIT, 챕터 생성 가능. 저장하지 않고 나가기: end_type=DISCARD, 이번 인터뷰의 음성·전사·질문 삭제(Object Storage 객체 포함), 챕터 생성 안 함 | INTERVIEW_END |

### 9-3. 상태 전이

**tb_trip_day.status**

| 현재 | 이벤트 | 다음 |
| --- | --- | --- |
| READY | 분석 시작(E07) | ANALYZING |
| ANALYZING | 분석 완료 / 전체 실패 | SCENE_READY / FAILED |
| FAILED(분석) | 분석 재요청(E07) | ANALYZING |

## 10. 무결성 · 저장 규칙

### 소유권·연결

- 모든 조회·변경에서 쿠키 사용자가 여행 소유자인지 검사한다(남의 데이터는 404).
- 사진·장면·질문·발화·문장·근거는 같은 일차(또는 같은 여행)에 속해야 한다. 표지 사진은 같은 여행, 대표 인용 발화·본문 사진은 같은 일차에 속해야 한다(저장 시 검사).
- 진행 중 여행은 1개(C-17). 사용자 행을 `SELECT … FOR UPDATE`로 잠근 트랜잭션에서 검사하고 만든다.
- 인터뷰 시작 후에는 해당 일차에 사진을 추가하거나 장면을 다시 만들 수 없다(API 409 `INTERVIEW_STARTED`). 인터뷰가 DISCARD되면 다시 가능하다.

### 답변·음성

- `ANSWERED` 질문은 비어 있지 않은 전사를 가진 USER 발화를 가진다. 전사가 비면 `SKIPPED`로 처리한다.
- 같은 질문의 중복 답변 요청은 이미 저장된 결과를 그대로 돌려준다(멱등).
- 완료된 답변의 전사·음성 연결은 수정하지 않는다. "다시 듣기"·"건너뛰기"는 아직 확정되지 않은 녹음을 버리는 동작이다.
- 대표 인용문은 연결된 USER 발화의 전사에서 그대로 발췌한다.

### 이야기 생성·재시도

- 공개하는 모든 문장에는 사진 또는 확정 답변 근거가 1개 이상 있어야 하며, 근거 존재뿐 아니라 문장 내용과의 일치도 검증한다.
- 문장과 근거를 한 트랜잭션으로 저장한 뒤 챕터를 DONE으로 바꾼다.
- 같은 대상의 진행 중 작업은 `active_key` 유니크로 1개만 허용한다. 중복 요청은 기존 jobId를 돌려준다.
- 문체 변경은 모든 일차의 새 버전이 완성된 뒤 한 트랜잭션에서 `current_yn`을 전환한다.

## 11. 데이터 삭제 (E18)

1. 사용자의 모든 여행을 `DELETING`으로 바꿔 업로드·생성·결과 반영을 차단하고 진행 중 작업을 취소한다.
2. 사진(`upload_status`)·발화(`status`)를 `DELETE_PENDING`으로 표시하고 Object Storage 객체(`users/{userId}/` 접두)를 삭제한다. 실패하면 객체 키와 DB 행을 남기고 재시도한다.
3. 객체 삭제 확인 후 순환 참조(`tb_trip.cover_photo_id`, `tb_chapter.photo_id`, `tb_chapter.highlight_voice_segment_id`)를 NULL로 푼다.
4. 자식 데이터부터 삭제한다: 문장 근거 → 문장 → 챕터 → 장면 기억 → 발화 → 질문 → 인터뷰 → 사진 → 장면 → 일차 → 여행 → 작업 → 사용자. (FK의 CASCADE는 마지막 안전망일 뿐이며, CASCADE만으로 지우면 Object Storage 파일이 남는다.)
5. 마지막에 쿠키를 만료시키고 204를 반환한다.

삭제 도중 실패하면 DB 데이터는 남아 있으므로 같은 요청을 다시 보내 이어서 지운다.

## 13. 명명 규칙

- 테이블은 `tb_` + 소문자 스네이크 케이스, 컬럼은 소문자 스네이크 케이스. 여부 컬럼은 `_yn`(CHAR 1, Y/N), 일시는 `_at`, 날짜는 `_date`, 객체 키는 `_key`.
- 사진·음원은 DB에 저장하지 않고 Object Storage 키만 저장한다. 임시 접근 URL은 저장하지 않는다.
- 삭제는 물리 삭제이며 11장의 절차를 따른다(`deleted_at` 소프트 삭제는 쓰지 않는다).

## 14. 확인이 필요한 부분

- 쿠키 이름·유효 기간, 쿠키 분실 시 복구 불가 정책(C-02, C-03).
- 소설(NOVEL) 문체를 추가할지(C-05). 추가하면 화면·프롬프트·코드값이 함께 필요하다.
- 재시도 한도와 챕터 작성 제한 시간(C-14), 장면 분할·공백 기준값(C-13), 책 엮기 부분 일차 포함 정책(C-16).
- 닉네임 변경 방법(화면 없음). 변경하더라도 쿠키는 유지한다.
- 한 계정을 여러 브라우저·기기에서 쓰려면 브라우저 토큰 테이블이 따로 필요하다(MVP 범위 밖).
- "저장하지 않고 나가기" 삭제 범위는 해당 인터뷰의 음성·전사·질문으로 정했다(9-2장 7번).
- "AI가 학습한다"는 업로드된 사진을 분석해 질문을 만드는 것이며, 사용자 데이터로 모델을 재학습하지 않는다.
